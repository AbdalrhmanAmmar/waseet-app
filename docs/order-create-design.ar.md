# إنشاء الطلب المباشر وإضافة اللون

تاريخ التنفيذ: 2026-09-18.

## النتيجة

أُلغيت السلة بالكامل من التطبيق، وأصبح إنشاء الطلب نموذجًا واحدًا متوافقًا مع حقول نموذج الداشبورد الموجود في `dashboard/src/pages/Orders/OrderCreate.tsx`. النموذج مشترك بين Merchant وSalesEmployee، ويحتوي على لون إلزامي مستقل لكل منتج. أدوار الإدارة والتوصيل تحتفظ بوظائفها وصلاحياتها الحالية.

## تجربة الاستخدام

1. يبدأ المستخدم من «طلب جديد» في شريط التنقل، أو من الرئيسية/الطلبات، أو من زر «إنشاء طلب» في بطاقة المنتج وتفاصيله. الدخول من تفاصيل المنتج يعبئ المنتج والكمية المختارة.
2. يُدخل اسم العميل، رقم الهاتف السوري، منطقة التوصيل والعنوان التفصيلي.
3. يختار المنتجات من نافذة بحث بالاسم أو الكود، مع الصور عند توفرها وحالة المخزون. تُحمَّل صفحات الكتالوج أثناء فتح الاختيار. المنتج المضاف والمنتج النافد غير قابلين للإضافة مرة أخرى.
4. لكل منتج: الكمية، سعر البيع القابل للتعديل، اللون الإلزامي، وإجمالي العنصر. يمكن حذف المنتج أو تعديل كميته بدل تكراره.
5. يظهر ملخص عدد المنتجات وعدد القطع وقيمة المنتجات ورسوم التوصيل والإجمالي المتوقع، مع زر مراجعة ثابت أسفل الشاشة.
6. قبل المراجعة تُحدَّث مناطق التوصيل وبيانات المنتجات المختارة. إذا نقص المخزون أو اختفت رسوم المنطقة، يتوقف الإرسال ويظهر سبب واضح مع بقاء بيانات المستخدم.
7. نافذة المراجعة تعرض العميل والعنوان والمنتجات وألوانها وأسعارها والإجمالي. يمكن العودة للتعديل دون فقدان البيانات.
8. بعد التأكيد والنجاح تظهر شاشة نجاح تتضمن رقم الطلب إذا أعاده الخادم، وزري عرض التفاصيل وإنشاء طلب آخر. اللون يظهر في تفاصيل الطلب عندما يُرجعه الخادم.

## التصميم

- واجهة عربية بمحاذاة واضحة، ألوان الهوية الخضراء، خلفية فاتحة وبطاقات مستقلة للأقسام.
- بطاقات منتجات بها صورة أو أيقونة بديلة، تحكم في الكمية، حقول معنونة ورسائل تحقق مرتبطة بالحقول.
- نوافذ اختيار ومراجعة من أسفل الشاشة، مع مراعاة Safe Area ولوحة المفاتيح على iOS.
- عرض مرن بحد أقصى 760px، واختبار الاستخدام على عرض هاتف 320px.
- فرق السعر عن سعر التاجر يظهر للتاجر فقط عندما تتوفر قيمة صالحة. لا تُخترع أسعار أو أرباح غير موجودة.

## قواعد البيانات والتحقق

| الحقل | القاعدة |
| --- | --- |
| اسم العميل | حرفان على الأقل بعد إزالة المسافات المحيطة |
| الهاتف | رقم سوري يبدأ بـ09 ويتكون من 10 أرقام؛ تحويل الأرقام العربية والفارسية إلى الإنجليزية |
| المنطقة | منطقة فعلية من API برسوم معروفة وغير سالبة؛ غياب الرسوم لا يعني توصيلًا مجانيًا |
| العنوان | أربعة أحرف على الأقل |
| المنتجات | منتج واحد على الأقل، دون تكرار كود المنتج |
| الكمية | عدد صحيح موجب لا يتجاوز المخزون المعروف |
| سعر البيع | موجب ومحدود، بمنزلتين عشريتين كحد أقصى |
| اللون | نص حر مطلوب لكل عنصر، بحد أقصى 50 حرفًا، وإزالة المسافات المحيطة قبل الإرسال |

لون المنتج نص حر لأن البيانات المدروسة لا توفر كتالوج ألوان مرتبطًا بمخزون مستقل لكل لون. لا توجد افتراضات عن الألوان المتاحة. إذا أضيفت variants فعلية إلى الخادم لاحقًا، يلزم ربط حقل الاختيار ومخزونه بعقد تلك variants.

## الربط بالخادم

العنوان الحالي لم يتغير:
`https://smart-broker-bcd9bzfvagd5f8dx.westus-01.azurewebsites.net/api/`

- `GET Product/all`: الكتالوج؛ دون طلب price-lists للتاجر.
- `GET Product/{id}`: تحديث بيانات المنتج المختار قبل المراجعة؛ دون merchant-price.
- `GET delivery-areas`: المناطق ورسومها.
- `POST orders`: بيانات العميل و`items`، وكل عنصر يحتوي على `productCode`, `quantity`, `actualSellPriceUSD`, `color`.
- التوكن يُرفق من عميل API الحالي في Authorization. لا يُضاف إلى URL.
- إجماليات الواجهة تقديرية؛ الخادم مسؤول عن القيمة النهائية والتحقق الأخير من المخزون والصلاحيات.
- استجابات `success: false` و`isSuccess: false` لا تتحول إلى نجاح حتى لو كان HTTP 200.

## المسودة والأخطاء

- المسودة محلية في ذاكرة الشاشة. لا يوجد تخزين دائم للسلة أو لمسودات الطلبات.
- الاختيار والمراجعة والتعديل لا يفقدون المسودة. المغادرة مع وجود بيانات تتطلب تأكيد تجاهلها.
- الحقول تُقفل أثناء التحقق والإرسال. يمنع قفل متزامن النقر المكرر من إنشاء طلبين.
- عند رفض واضح من الخادم تبقى البيانات للتعديل وإعادة المحاولة.
- عند انقطاع الاتصال أو خطأ 5xx، تكون نتيجة الإنشاء غير مؤكدة؛ لا يحدث POST تلقائي آخر، ويُطلب مراجعة آخر الطلبات قبل إنشاء طلب جديد.
- النجاح يمسح المسودة، و«إنشاء طلب آخر» يبدأ نموذجًا فارغًا.
- فشل تحديث المنتجات أو المناطق لا يُخفى؛ يتوقف فتح المراجعة حتى تتوفر بيانات صالحة.

## التحقق وحدوده

- TypeScript وESLint: ناجحان.
- اختبارات الوحدات: 23 ناجحة، تشمل payload اللون والأرقام والأسعار والتحقق وأخطاء API.
- اختبارات الواجهة: نجحت الجولة الشاملة (46 سيناريو)، ثم نجحت الجولة النهائية المركزة (12 سيناريو) بما فيها اختبار إضافي لطلب متعدد المنتجات والضغط المزدوج؛ الإجمالي 47 سيناريو مختلفًا.
- تصدير Expo للويب وiOS وAndroid: ناجح.
- اختبارات الإنشاء تستخدم API محاكى، ولم تُنشأ طلبات على الخادم الحقيقي. يلزم تجربة حساب فعلي للتحقق التشغيلي؛ ولم تُجرَ تجربة على جهاز iOS/Android فعلي.
- تصدير حزمة iOS/Android يثبت سلامة bundling؛ لا يعادل بناء native أو اختبار إيماءات النظام ولوحة المفاتيح على الجهاز.
