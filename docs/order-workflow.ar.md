# تفاصيل الطلب وتعديله: الداخلي والخارجي

تنفيذ 19 سبتمبر 2026، اعتمادًا على `dashboard/src/pages/Orders` وبناءً على طلب إتاحة التجربة للأدوار الأربعة. التغيير في تطبيق Expo فقط؛ صلاحيات الخادم لم تُعدّل.

## الأدوار ومصادر البيانات

- التاجر والمبيعات والإدارة والمندوب: تفاصيل الطلب، سجل العمليات، تغيير الحالة، حل التعثر، وتعديل الطلب الداخلي غير النهائي.
- مصدر الإدارة يبقى `GET orders`، ومصدر المندوب `GET orders/my-deliveries`. نطاق الطلبات المسموح للمستخدم رؤيتها يحدده الخادم.
- سعر التاجر والربح يظهران للتاجر فقط. المبيعات لا تفتح تفاصيل المنتج ولا تستدعي `Product/{id}` أو `Product/all` ضمن هذه الرحلة.
- إنشاء الطلب يبقى للتاجر والمبيعات. إضافة صلاحيات التعديل لا تضيف إنشاء طلب للإدارة أو المندوب.

## تحديد جهة التوصيل

قراءة `GET delivery-areas` ومطابقة `customerArea` مع `city` أو `oliveryAreaName` بعد تطبيع النص العربي. `isInternalDelivery` يجب أن يكون Boolean صريحًا. عدم المطابقة أو غياب الحقل أو تعارض مناطق بنفس الاسم أو فشل الطلب يجعل النوع «غير محدد» ويقفل الكتابة حتى إعادة التحقق. المنطقة الجديدة في التعديل يجب أيضًا أن تكون داخلية؛ لا يكفي أن تكون المنطقة الأصلية داخلية.

## قواعد الحالة

| الحالية | الانتقالات الداخلية |
| --- | --- |
| Pending | Processing، Cancelled، Stuck |
| Processing | Confirmed، Cancelled، Stuck |
| Confirmed | Out for Delivery، Cancelled، Stuck |
| Out for Delivery | Delivered، Refused on Delivery، Postponed، Stuck |
| Postponed | Out for Delivery، Cancelled، Stuck |
| Delivered / Refused on Delivery | Closed إذا كانت الحالة الحالية غير نهائية وفق الخادم |
| Stuck | Processing مع ملاحظة حل إلزامية |
| Cancelled / Closed | لا يوجد |

الخارجي: `Processing → Confirmed / Stuck`، و`Stuck → Processing` لحل التعثر بملاحظة. بقية المراحل تتولاها جهة التوصيل. الحالات المتاحة تُقرأ من `GET orders/statuses`، ولا تُخترع قيم بديلة. التعثر يتطلب سببًا، وحلّه يتطلب ملاحظة، بحد 500 حرف. لا يمكن القفز على مراحل الدورة أو الرجوع إلى مرحلة سابقة. الحالة غير المعروفة مقفلة للتغيير.

تفتح النافذة بالتفاصيل والمناطق والحالات الحديثة، ثم اختيار ومراجعة وتأكيد. قبل POST تُعاد قراءة الثلاثة مباشرة للتحقق من أن الحالة لم تتغير وأن الانتقال ما زال متاحًا. ينطبق ذلك على أزرار قوائم الإدارة والمندوب وعلى تفاصيل كل الأدوار.

## تعديل الطلب

مسار `/{role}/edit-order` لكل دور يعيد استخدام شاشة واحدة. تشمل بيانات العميل والهاتف السوري والمنطقة الداخلية والعنوان، وعناصر الطلب: الكود، الكمية الصحيحة الموجبة، سعر البيع، واللون الإلزامي حتى 50 حرفًا. يمكن إضافة وحذف العناصر، مع منع الأكواد المكررة والقائمة الفارغة والأسعار غير الصالحة. لا تُجلب تفاصيل منتجات المبيعات؛ إدخال الكود في التعديل مماثل للداشبورد، والتحقق من وجود المنتج ومخزونه من مسؤولية الخادم.

قبل الحفظ تظهر مراجعة بيانات العميل وقائمة العناصر الكاملة والإجمالي. طلب PUT يرسل العميل وكل العناصر فقط، دون إجمالي مفروض من الهاتف أو حقول التاجر. أرقام الكمية والأسعار تقبل الإدخال العربي. عند مغادرة مسودة معدلة تظهر نافذة تأكيد. فشل الحفظ يبقي القيم المكتوبة وملاحظات الحالة، ولا يعرض نجاحًا وهميًا.

قبل PUT يُعاد تحميل الطلب والمناطق والحالات، وتُقارن نسخة الطلب بنسخة فتح التعديل لمنع استبدال تغييرات لاحقة ببيانات قديمة. هذا تحقق من جهة العميل؛ منع السباق بين آخر GET وPUT بصورة ذرّية يحتاج دعم إصدار/ETag أو تحقق تزامن من الخادم.

## التفاصيل والبوليصة

بطاقة الحالة والإجمالي المسجل، جهة التوصيل، إجراءات الطلب، بيانات العميل مع الاتصال ونسخ الهاتف، المنتجات والألوان والكميات والأسعار، ملخص مالي، وحالة التوصيل منفصلة عن حالة الطلب. السجل مرتب من الأحدث، يعرض خمسة أحداث ثم المزيد، مع المنفّذ والتاريخ والملاحظة وزر تحديث.

البوليصة HTML عربية بمقاس A5، تستخدم الإجمالي المسجل دون إعادة إضافة رسوم التوصيل، ولا تعرض الربح أو سعر التاجر. يُهرب النص قبل إدراجه في HTML. الويب يفتح معاينة مستقلة تتيح طباعة/حفظ PDF من المتصفح. iOS/Android يستخدمان `expo-print` و`expo-sharing` للطباعة ومشاركة PDF. أضيفت نسخ متوافقة مع SDK 57. لا يُرسل PDF إلى خدمة خارجية تلقائيًا.

## مشكلات الطلب

تعرض تفاصيل الطلب قسم «مشكلات الطلب» للتاجر وموظف التاجر وموظف المبيعات وموظف الإدارة، ولا تعرضه للمندوب. يُقرأ القسم من `GET orders/{id}/issues`، ويرتب المشكلات من الأحدث، ويعرض الحالة والمنشئ والتاريخ ومعلومات الحل، مع خمسة عناصر أولًا وزر لعرض المزيد.

يمكن إنشاء مشكلة فقط بعد اكتمال التوصيل: `deliveryStatus = Delivered` للطلبات الداخلية، أو `oliveryStatus = delivered` للطلبات الخارجية. وصف المشكلة إلزامي من 5 إلى 500 حرف. حل المشكلة حصري لدور `ManagementEmployee`، ويظهر زر الحل فقط للمشكلة المفتوحة التي يعيد الخادم لها `canResolve = true`. ملاحظة الحل إلزامية من 5 إلى 500 حرف. التحقق في الواجهة يستخدم Zod، وتعيد الواجهة قراءة أحدث بيانات الطلب أو المشكلات قبل أي كتابة. يجب أن يفرض الخادم قيد دور الإدارة أيضًا على مسار الحل، لأن إخفاء الزر في التطبيق ليس بديلًا عن تفويض الخادم.

## عقد الخادم المطلوب

| الطريقة والمسار | الوظيفة / الحقول |
| --- | --- |
| GET orders/{id} | orderId، status، customerName، customerMobile، customerArea، customerAddress، items، orderTotalUSD، deliveryFee؛ deliveryStatus عند توفره |
| GET delivery-areas | deliveryAreaId، city، fee، isInternalDelivery، oliveryAreaName |
| GET orders/statuses | status، isTerminal |
| GET orders/{id}/history | fromStatus، toStatus، changedAt، changedByRole/changedByActorType، changedById، note |
| POST orders/{id}/status | targetStatus، note عند إدخاله؛ يستخدم أيضًا لحل التعثر إلى Processing |
| PUT orders/{id} | customerName، customerMobile، customerArea، customerAddress، items[{productCode,quantity,actualSellPriceUSD,color}] |
| GET orders/{id}/issues | قائمة مشكلات الطلب مع status وdescription وcanResolve وبيانات الإنشاء والحل |
| POST orders/{id}/issues | description بطول 5–500 حرف؛ متاح بعد اكتمال التوصيل |
| POST orders/issues/{issueId}/resolve | resolutionNote بطول 5–500 حرف؛ لحل المشكلة المفتوحة المسموح بحلها |

كل الطلبات تستخدم Bearer token من الجلسة المشتركة. يلزم تمكين القراءة والكتابة للأدوار المقصودة على الخادم، والتحقق من ملكية/إسناد الطلب وصحة الانتقال والمنتجات والأسعار هناك. عند 403 تعرض الواجهة رفض الصلاحية وتحافظ على المسودة؛ لا تستخدم endpoint بديلًا ولا تتجاوز رفض الخادم.

## التحقق

اختبارات الوحدة في `tests/order-workflow.test.ts` تغطي تطبيع المناطق، الانتقالات، النهائية، التعثر، إعادة التحقق قبل الكتابة، التعارض، التحقق من العناصر، والبوليصة.

اختبارات المتصفح في `tests/e2e/order-workflow.spec.ts` تغطي الأدوار الأربعة، الداخلي والخارجي، رفض الصلاحية، الحفاظ على المسودة، تغيّر الحالة أو المنطقة، إضافة/حذف المنتجات، المغادرة، ومعاينة البوليصة على شاشة صغيرة. جميع هذه الاختبارات تستخدم API محاكى؛ لم تُرسل تغييرات إلى طلبات حقيقية. التحقق الأصلي للطباعة والمشاركة على جهاز فعلي، والتحقق بحسابات الخادم بعد إصلاح صلاحياته، ما زالا مطلوبين قبل الاعتماد التشغيلي.

نتائج التحقق: نجحت `typecheck` و`lint` و37 اختبار وحدة، و46 سيناريو متصفح تشمل دورة الطلب والقوائم وإنشاء الطلب ومنتجات المبيعات وصلاحيات التوجيه. نجح تصدير حزم iOS وAndroid وWeb. هذه نتيجة بناء واختبارات محاكاة، وليست إثباتًا لصلاحيات الخادم الفعلية أو تشغيل نافذة مشاركة PDF على جهاز حقيقي.

معاينات فعلية من اختبار الويب ببيانات محاكاة: [تفاصيل الطلب بعرض 320](redesign-preview/order-details-320.png)، [مراجعة تعديل الطلب](redesign-preview/order-edit-review.png). بعد تحسين نافذة المراجعة، أُعيد تشغيل سيناريوهات دورة الطلب الخمسة عشر على التصدير النهائي ونجحت جميعها.
