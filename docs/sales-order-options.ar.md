# منتجات وإنشاء طلبات موظف المبيعات

## مصدر البيانات

- يطبّع الدور `sales` إلى `SalesEmployee` حسب إعداد الجلسة الحالي.
- مصدر منتجات المبيعات الوحيد هو `GET /api/Product/order-options`، عبر عميل التطبيق الذي يضيف `Authorization: Bearer`.
- الاستجابة المعتمدة هي `{ isSuccess: true, data: [...] }` التي أرسلها صاحب المشروع. القائمة كاملة، دون pagination أو معاملات صفحة مخترعة.
- endpoint مستقل باسم `salesOrderOptions` في `src/api/sales-employee/index.ts`، والكاش مرتبط بمعرّف المستخدم ويُمسح مع إنهاء الجلسة وفق آلية التطبيق الحالية.
- التاجر يستمر في استخدام `Product/all` و`Product/{id}`.

## واجهة المبيعات

قائمة بطاقات تتناسب مع البيانات المختصرة: الاسم والكود والسعر الأصلي والسعر المتوقع، مع السعر المتوقع المطبق عندما يكون موجودًا ومختلفًا. تعرض القيم الناقصة «غير محدد»، وتحافظ على الصفر الحقيقي.

لا يُنسخ `merchantSellPrice` إلى نموذج منتجات المبيعات، ولا يُستخدم لتعبئة السعر أو عرضه. لا توجد صور أو فئات أو شارات توفر وهمية. البحث محلي بالاسم والكود ويدعم الأرقام العربية، مع تحديث وسحب للتحديث وحالات تحميل وخطأ وفراغ منفصلة.

زر البطاقة ينشئ طلبًا مع المنتج المختار. لا تفتح البطاقة تفاصيل المنتج، والمسار `/sales-employee/product` يعيد التوجيه للمنتجات دون تركيب شاشة التفاصيل أو إجراء طلب API لها. صلاحيات مسارات الأدوار الأخرى تظل محمية بواسطة حارس الأدوار الحالي.

## إنشاء الطلب

- منتقي المنتجات يستخدم المصدر نفسه، ويمنع إضافة المنتج مرتين مع السماح بتعديل كميته.
- سعر البيع الافتراضي: `effectiveExpectedSellPrice` ثم `expectedSellPrice`، وإلا إدخال يدوي. لا يُستخدم السعر الأصلي أو سعر التاجر كبديل.
- يحتفظ النموذج بالعميل والهاتف والمنطقة والعنوان، والكمية والسعر الفعلي واللون لكل منتج، والمراجعة قبل التأكيد.
- للمبيعات: الكمية عدد صحيح موجب، والخادم هو مصدر التحقق من المخزون لأن الاستجابة لا تحتوي مخزونًا. يبقى تحقق مخزون التاجر كما هو.
- قبل المراجعة تُحدث مناطق التوصيل ثم قائمة `order-options` مرة واحدة لكل الطلب، دون استدعاء `Product/{id}`. يعاد ربط المنتجات مع الحفاظ على السعر والكمية واللون التي عدّلها المستخدم.
- اختفاء منتج من الخيارات أو فشل التحديث يمنع المراجعة، ويحفظ المسودة لتعديلها وإعادة المحاولة.
- الإرسال يستخدم عقد `POST /api/orders` الحالي: بيانات العميل و`items: [{ productCode, quantity, actualSellPriceUSD, color }]`.
- الرفض المعروف من الخادم يعرض رسالته ويحتفظ بالمدخلات. منع الإرسال المكرر وحماية نتيجة الإرسال غير المؤكدة يعملان كما في النموذج الحالي.

## التحقق

اختبارات وحدة تغطي تنقية سعر التاجر، أولوية الأسعار، غياب المخزون، والتأكد من بقاء تحقق مخزون التاجر. اختبارات واجهة بمحاكاة API تغطي `sales`، مصدر الطلبات والتوكن، عدم طلب تفاصيل المنتجات، عرض 320px، البحث، الأسعار الناقصة، الطلب متعدد المنتجات، الرفض واختفاء المنتج، و403 والاستجابة غير الصالحة والقائمة الفارغة.

لا يتضمن التحقق إرسال طلب حقيقي إلى خادم الإنتاج، ولا اختبارًا على جهاز iOS/Android فعلي.

النتيجة: نجحت فحوص TypeScript وESLint والتنسيق، و30 اختبار وحدة، و32 اختبار واجهة تشمل المنتجات والتفاصيل وإنشاء الطلب وحراس الأدوار. أعيد تشغيل اختبارات المبيعات الأربعة بعد ضبط خط البحث ولقطات المعاينة فنجحت. نجح أيضًا تصدير Expo للويب وiOS وAndroid.
