# حالات اختبار يدوية — صلاحيات الطلبات الداخلية في تطبيق الموبايل

> النطاق: iOS وAndroid · الاختبار يدوي · الأدوار: Merchant وMerchantEmployee وSalesEmployee وDeliveryAgent وManagementEmployee · Admin خارج النطاق.

## 1. الملخص التنفيذي

تتحقق هذه الخطة من ظهور إجراءات تغيير حالة الطلب الداخلي أو اختفائها بحسب دور المستخدم والحالة الحالية للطلب. تُنفّذ الحالات على iOS وAndroid، وتتعامل مع شروط Owner only وAssigned only على أنها محققة لأن المختبر يستخدم حسابًا مالكًا أو مُسنَدًا له الطلب. تنظم الخطة الاختبار بطريقة Status Sweep: 13 حالة طلب لكل دور، بإجمالي 65 حالة تغطي 85 تأكيدة صلاحية. يجب التحقق من الحالة المعروضة قبل الحكم على الصلاحية، وتسجيل النتيجة الفعلية وPass/Fail وإرفاق لقطة شاشة.

## 5. تعريف «مخفي» ومسارات الفحص

يُعد الإجراء مخفيًا فقط إذا تأكد المختبر من غيابه بعد تمرير الشاشة كاملة، ومن جميع نقاط الدخول المتاحة. زر معطل أو عنصر خارج مساحة العرض لا يحقق شرط الإخفاء.

يجب فحص المسارات التالية في كل نتيجة سلبية:

- شاشة تفاصيل الطلب وبطاقة الإجراءات.
- أي قائمة إجراءات أو قائمة منسدلة وأيقونة الثلاث نقاط.
- السحب يمينًا ويسارًا على صف الطلب.
- الضغط المطوّل على صف الطلب أو بطاقة الحالة.
- شاشة التعديل أو أي إجراء سياقي ظاهر منها.
- الرابط العميق المعروف لتفاصيل الطلب إن كان متاحًا في نسخة الاختبار.
- كامل الشاشة بعد التمرير من أولها إلى آخرها.

## 6. تحذير الحالة الحالية

لا يجوز الحكم على الصلاحية باستخدام طلب في حالة غير حالة From المحددة. قبل فحص الظهور، يقرأ المختبر نوع الطلب والحالة من الشاشة ويطابقهما مع شروط الحالة. غياب Dispatch في Processing لا يثبت منعه؛ يجب فحصه في Confirmed وReady for Dispatch. أي عدم تطابق في الحالة يبطل نتيجة الحالة ويستلزم إعادة التحضير.

### 7.2 بيانات الطلب

- طلب داخلي حقيقي في مدينة داخلية معتمدة في البيئة، مثل دمشق أو اللاذقية، ويظهر في التفاصيل أنه ليس موجّهًا عبر Olivery.
- 9 نسخ أو نقاط إعادة ضبط لطلب عادي بالحالات: Processing، Confirmed، Ready for Dispatch، Stuck، Out for Delivery، Postponed، Delivered، Cancelled، Refused on Delivery.
- 4 نسخ أو نقاط إعادة ضبط لطلب نوعه Return بالحالات: Processing، Confirmed، returned_in_progress، returned_delivered.
- حسابات Merchant وMerchantEmployee وSalesEmployee ترى الطلب المطلوب وفق بيانات البيئة. حساب DeliveryAgent مُسنَد للطلب، ولمرتجعات #12 و#13 يكون مسجلًا في دمشق. حساب ManagementEmployee يرى الطلب المطلوب.
- بعد تنفيذ إجراء يغيّر الحالة، يجب إعادة الطلب إلى حالة From أو استخدام نسخة مستقلة قبل تجربة الإجراء التالي.

### 7.3 الفجوة التشغيلية الحرجة

طريقة تجهيز الطلب في حالة محددة غير موثقة في المتطلبات الحالية. قبل بدء التنفيذ يجب أن يحدد فريق البيئة واحدًا من الآتي: بيانات seed قابلة لإعادة التشغيل، سكربت reset معتمد، API تجهيز خاص ببيئة QA، snapshot لقاعدة الاختبار، أو مستخدم إعداد يغير الحالة. استخدام مستخدم إعداد لا يجعله دورًا مختبرًا، وAdmin يظل خارج حالات الصلاحيات. لا تبدأ الحالات التي لا تتوفر لها حالة From صحيحة، وسجّلها Blocked بسبب بيانات الاختبار بدل Pass/Fail.

## 12. المخاطر والفجوات

| الخطر/الفجوة | الأثر | الإجراء المطلوب |
| --- | --- | --- |
| طريقة تجهيز أو Reset الحالات غير محددة | قد يتعذر تنفيذ معظم الحالات أو إعادة تجربة الإجراءات المتعددة | اعتماد seed/reset/API تجهيز قبل بدء الدورة |
| حسابات الاختبار ومعرفاتها غير مذكورة | لا يمكن إثبات شرط Owner/Assigned المبسط | تعبئة جدول الحسابات وربط كل طلب بالحساب الصحيح |
| عقد الخادم قد يرفض دورًا تسمح به الواجهة | ظهور الإجراء لا يثبت نجاحه | تسجيل 403 وRequest ID وفتح عيب Backend/تكامل |
| Ready for Dispatch قد لا يكون موجودًا في catalog البيئة | تتعطل S2/S3 و#1b/#4 | التأكد من GET orders/statuses أو تجهيز البيئة قبل الاختبار |
| اختلاف تسمية Solve Pending عن الواجهة الحالية | قد يختبر المختبر عنصرًا خاطئًا | استخدام الانتقال Stuck → Processing كهوية أساسية وتسجيل النص الفعلي |
| تعريف المدينة الداخلية ديناميكي | اختيار مدينة غير داخلية يحول الاختبار إلى تدفق خارجي | التحقق من بطاقة جهة التوصيل أو إعداد المنطقة قبل كل حالة |
| روابط deep link المعروفة غير موثقة بالكامل | قد يبقى مسار بديل غير مفحوص | تزويد QA بقائمة routes المدعومة في نسخة الاختبار |
| إجراءات الإلغاء والإغلاق والمرتجع تغير البيانات أو التسوية | صعوبة إعادة الاستخدام وخطر تلويث البيانات | استخدام بيانات مخصصة وReset موثوق وعدم استخدام بيانات إنتاج |
| اختلاف iOS وAndroid في القوائم والسحب | احتمال وجود إجراء بديل على منصة واحدة | تنفيذ كل حالة على المنصتين وتوثيق الفرق |
| حالات Return تحتاج علاقات وبيانات مالية صحيحة | قد يُحجب الإجراء لسبب بيانات لا لصلاحية الدور | تجهيز مرتجع صالح والتحقق من نوعه وحالته والتسوية قبل الحكم |
